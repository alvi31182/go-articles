# Transaction Demarcation — перевод статьи

> Оригинал: Transaction Demarcation — Doctrine ORM

## Разграничение транзакций

Разграничение транзакций — это определение границ ваших транзакций. Делать это правильно крайне важно: если ошибиться, можно сильно просадить производительность. Во многих базах данных и слоях абстракции (например, PDO) по умолчанию включён режим autocommit. Это значит, что каждый SQL-запрос оборачивается в маленькую транзакцию. Без явного разграничения с вашей стороны это быстро приводит к лишним накладным расходам, ведь транзакции стоят недёшево.

В большинстве случаев Doctrine ORM уже заботится о корректных границах транзакций: все операции записи (INSERT/UPDATE/DELETE) ставятся в очередь до тех пор, пока не будет вызван `EntityManager#flush()`. Этот вызов оборачивает все изменения в одну транзакцию.

Тем не менее Doctrine ORM позволяет (и поощряет) вам брать управление границами транзакций на себя. Ниже два подхода к работе с транзакциями в Doctrine ORM.

## Подход 1. Неявное управление

Первый вариант — использовать неявную обработку транзакций, которую предоставляет `EntityManager`. Возьмём такой пример без явного разграничения:

```php
<?php

// $em instanceof EntityManager

$user = new User;
$user->setName('George');

$em->persist($user);
$em->flush();
```

Поскольку мы не начинаем транзакцию вручную, `EntityManager#flush()` сам откроет её, а затем зафиксирует или откатит. Такое поведение возможно благодаря тому, что ORM агрегирует DML-операции. Этого достаточно, если вся работа с данными в рамках юнита выполняется через доменную модель и сам ORM.

## Подход 2. Явное управление

Альтернатива — управлять транзакционными границами напрямую через `Doctrine\DBAL\Connection`. Код будет выглядеть так:

```php
<?php

// $em instanceof EntityManager

$em->getConnection()->beginTransaction(); // выключаем autocommit

try {
    // ... выполняем работу
    $user = new User;
    $user->setName('George');

    $em->persist($user);
    $em->flush();

    $em->getConnection()->commit();
} catch (Exception $e) {
    $em->getConnection()->rollBack();
    throw $e;
}
```

Явное разграничение нужно, когда в юнит работы попадают кастомные операции на уровне DBAL или когда вы вызываете методы `EntityManager`, которым требуется активная транзакция. В таких случаях будет выброшено `TransactionRequiredException`.

## Control abstractions

Удобнее всего работать с транзакциями через `Connection#transactional($func)` и `EntityManager#wrapInTransaction($func)`. Эти абстракции гарантируют, что вы не забудете сделать rollback, и сокращают код. Эквивалент предыдущего примера:

```php
<?php

// transactional с объектом Connection
// $conn instanceof Connection
$conn->transactional(function ($conn) {
    // ... выполняем работу
    $user = new User;
    $user->setName('George');
});

// transactional с EntityManager
// $em instanceof EntityManager
$em->wrapInTransaction(function ($em) {
    // ... выполняем работу
    $user = new User;
    $user->setName('George');
    $em->persist($user);
});
```

Разница между `Connection#transactional($func)` и `EntityManager#transactional($func)` (синоним `wrapInTransaction`) в том, что второй перед коммитом вызывает `flush()`, а при исключении закрывает `EntityManager` в дополнение к откату транзакции.

## Обработка исключений

* При неявном разграничении и ошибке во время `EntityManager#flush()` транзакция автоматически откатывается, а `EntityManager` закрывается.
* При явном — транзакцию нужно откатить сразу же и закрыть `EntityManager`, вызвав `EntityManager#close()`, после чего экземпляр следует выбросить (как в предыдущем примере). Control abstractions помогают сделать это аккуратно.

Если ловите `Exception`, обычно нужно пробрасывать исключение дальше. Если собираетесь восстанавливаться после конкретных ошибок, ловите их явно в отдельных блоках `catch`, но не забывайте откатывать транзакцию и закрывать `EntityManager`. Те же базовые правила обработки исключений (логируйте или пробрасывайте, но не делайте всё сразу) действуют и здесь.

После такой процедуры все ранее управляемые или удалённые сущности становятся отсоединёнными. Их состояние фиксируется на момент отката транзакции и не «откатывается» автоматически — значит, объекты оказываются рассинхронизированы с базой. Приложение может продолжать их использовать, осознавая, что данные потенциально устарели.

Если нужно начать новый юнит работы после исключения, создайте новый `EntityManager`.

## Поддержка блокировок

Doctrine ORM из коробки поддерживает пессимистические и оптимистические блокировки, позволяя точно контролировать стратегии для конкретных сущностей.

### Оптимистические блокировки

Классические транзакции подходят для контроля конкурентного доступа в рамках одного запроса. Но они не должны растягиваться на «время раздумий» пользователя между запросами. Долгая «бизнес-транзакция», растянутая на несколько HTTP-запросов, подразумевает несколько отдельных транзакций базы. Значит, часть ответственности за контроль конкурентности ложится на приложение.

Doctrine поддерживает оптимистическую блокировку через версионное поле. Сущность, которую нужно защитить от конкурирующих изменений, получает поле версии — целое число (`integer`) или метку времени (`datetime`). Когда изменения такой сущности сохраняются в конце длинной бизнес-сессии, версия сравнивается с версией в базе. Если они не совпадают, выбрасывается `OptimisticLockException`, сигнализируя, что объект уже изменён кем-то ещё.

Версионное поле объявляется так (пример с целым числом):

```php
<?php

class User
{
    // ...
    #[Version, Column(type: 'integer')]
    private int $version;
    // ...
}
```

Можно использовать `datetime` (отображается в SQL timestamp/datetime):

```php
<?php

class User
{
    // ...
    #[Version, Column(type: 'datetime')]
    private DateTime $version;
    // ...
}
```

Предпочтительнее числа, а не временные метки: в высококонкурентной среде таймстемпы могут конфликтовать из‑за ограниченной точности.

Если конфликт версий произошёл во время `EntityManager#flush()`, будет выброшен `OptimisticLockException`, а текущая транзакция откатывается (или помечается на откат). Исключение можно поймать и обработать: показать конфликт пользователю, обновить объекты в новой транзакции и попробовать снова и т.п.

Из‑за share-nothing архитектуры PHP между отображением формы и сохранением сущности может пройти столько же, сколько таймаут сессии. Если за это время объект кто-то изменит, лучше узнать об этом как можно раньше — прямо при загрузке сущности.

Проверить версию можно при `EntityManager#find()`:

```php
<?php

use Doctrine\DBAL\LockMode;
use Doctrine\ORM\OptimisticLockException;

$theEntityId = 1;
$expectedVersion = 184;

try {
    $entity = $em->find('User', $theEntityId, LockMode::OPTIMISTIC, $expectedVersion);
    // работаем с сущностью
    $em->flush();
} catch (OptimisticLockException $e) {
    echo "Sorry, but someone else has already changed this entity. Please apply the changes again!";
}
```

Или через `EntityManager#lock()`:

```php
<?php

use Doctrine\DBAL\LockMode;
use Doctrine\ORM\OptimisticLockException;

$theEntityId = 1;
$expectedVersion = 184;

$entity = $em->find('User', $theEntityId);

try {
    // проверяем версию
    $em->lock($entity, LockMode::OPTIMISTIC, $expectedVersion);
} catch (OptimisticLockException $e) {
    echo "Sorry, but someone else has already changed this entity. Please apply the changes again!";
}
```

### Важные замечания по реализации

Легко ошибиться, если сравнивать «не те» версии. Пример с Алисой и Бобом, редактирующими блог-пост:

1. Алиса читает заголовок «Foo», версия 1 (GET).
2. Боб читает заголовок «Foo», версия 1 (GET).
3. Боб меняет заголовок на «Bar», версия становится 2 (POST).
4. Алиса пытается поменять заголовок на «Baz» (POST).

Перед тем как применить изменение от Алисы, нужно снова прочитать пост из базы и убедиться, что версия всё ещё 1 (в сценарии выше это уже не так).

Чтобы оптимистическая блокировка работала, добавьте версию в скрытое поле формы (или положите в сессию). Иначе вы не сможете проверить, что версия та же, что и при первоначальной загрузке формы, и потеряете обновления, от которых хотели защититься.

Форма (GET):

```php
<?php

$post = $em->find('BlogPost', 123456);

echo '<input type="hidden" name="id" value="' . $post->getId() . '" />';
echo '<input type="hidden" name="version" value="' . $post->getCurrentVersion() . '" />';
```

Обработчик изменения заголовка (POST):

```php
<?php

$postId = (int) $_GET['id'];
$postVersion = (int) $_GET['version'];

$post = $em->find(
    'BlogPost',
    $postId,
    \Doctrine\DBAL\LockMode::OPTIMISTIC,
    $postVersion
);
```

### Пессимистические блокировки

Doctrine ORM поддерживает пессимистические блокировки на уровне базы. Собственная реализация не используется — применяются стандартные SQL-команды и специфичный синтаксис СУБД для получения строковых блокировок. Любая сущность может участвовать в пессимистической блокировке — никаких специальных метаданных не нужно.

Но чтобы это работало, нужно отключить autocommit и обернуть кейс в транзакцию («Подход 2» выше). Если попытаться взять пессимистическую блокировку без активной транзакции, Doctrine ORM выбросит исключение.

Доступны два режима:

* `Doctrine\DBAL\LockMode::PESSIMISTIC_WRITE` — блокирует строки от конкурентных чтений и записей.
* `Doctrine\DBAL\LockMode::PESSIMISTIC_READ` — блокирует другие запросы, пытающиеся обновить или захватить строки в write-режиме.

Использовать пессимистические блокировки можно четырьмя способами:

1. `EntityManager#find($className, $id, \Doctrine\DBAL\LockMode::PESSIMISTIC_WRITE)` либо `...PESSIMISTIC_READ`.
2. `EntityManager#lock($entity, \Doctrine\DBAL\LockMode::PESSIMISTIC_WRITE)` либо `...PESSIMISTIC_READ`.
3. `EntityManager#refresh($entity, \Doctrine\DBAL\LockMode::PESSIMISTIC_WRITE)` либо `...PESSIMISTIC_READ`.
4. `Query#setLockMode(\Doctrine\DBAL\LockMode::PESSIMISTIC_WRITE)` либо `...PESSIMISTIC_READ`.
